# AGENTS.md — redid

## О проекте

`redid` — веб-приложение с онлайн-листами персонажей для Cyberpunk RED и поддержкой пользовательских наборов навыков.

Текущий этап: пользователи, регистрация и аутентификация. Персонажи и наборы навыков будут реализованы позднее и не должны проектироваться заранее без отдельной задачи.

## Технологический стек

- Python 3.12+;
- FastAPI;
- Pydantic v2 и `pydantic-settings`;
- PostgreSQL;
- SQLAlchemy 2.x в асинхронном режиме;
- `asyncpg`;
- Alembic;
- pytest;
- Docker и Docker Compose.

Не добавлять новые библиотеки, инфраструктурные компоненты и архитектурные паттерны без практической необходимости.

## Архитектурные принципы

Проект строится как модульный монолит с упрощённым DDD.

- Группировать код по функциональным областям, а не по глобальным техническим слоям.
- HTTP-слой отвечает за транспорт: валидацию входа, зависимости, коды ответа и сериализацию.
- Бизнес-сценарии размещать в сервисах и не связывать с FastAPI.
- Запросы к БД инкапсулировать в репозиториях, когда это отделяет сценарий от SQLAlchemy или устраняет дублирование.
- SQLAlchemy-модели не передавать напрямую через публичный API.
- Pydantic-схемы не использовать как доменные сущности по умолчанию.
- Транзакция должна охватывать целый бизнес-сценарий. Решение о `commit` не должно быть случайно размазано по репозиториям.
- Зависимости направлять от сценария к небольшим контрактам только там, где существует реальная точка вариативности или это заметно упрощает тестирование.
- Не создавать отдельные `domain/application/infrastructure/presentation`, command bus, event bus, unit of work, generic repository, фабрики и базовые классы «на будущее».

DDD, SOLID и KISS применяются совместно:

1. Сначала выбрать самое простое корректное решение.
2. Отделить бизнес-правило от транспорта и хранения данных.
3. Добавлять абстракцию только для существующей вариативности, повторения или тестовой границы.
4. Уметь объяснить, какую конкретную проблему решает каждый дополнительный слой.

## Пользователи и OAuth

В приложении нет логина, пароля, имени пользователя и отдельной ручной регистрации. Первый успешный вход через OAuth создаёт пользователя.

На первом этапе реализуется только Яндекс, но сервис аутентификации не должен зависеть от деталей Яндекс API. Возможность добавить других провайдеров — известная точка расширения, поэтому небольшой контракт OAuth-провайдера оправдан.

Минимальная модель данных:

- `users`: внутренний UUID, URL аватара, даты создания и обновления;
- `oauth_accounts`: UUID, ссылка на пользователя, код провайдера, внешний идентификатор пользователя, дата создания;
- уникальность пары `(provider, provider_user_id)`;
- не более одного аккаунта одного провайдера на пользователя: `(user_id, provider)`.

Внешний идентификатор провайдера обязателен, даже если приложение визуально использует только аватар. Email, имя и OAuth access token провайдера не сохранять без нового требования.

Поток входа:

1. Сформировать криптографически стойкий OAuth `state` как подписанное короткоживущее значение.
2. Передать `state` в URL авторизации Яндекса; cookie для него не использовать.
3. На callback до обмена authorization code проверить наличие, подпись, структуру и срок действия `state`.
4. Обменять code на токен провайдера и получить внешний ID и аватар.
5. Найти OAuth-аккаунт либо атомарно создать пользователя и аккаунт.
6. Обновить аватар существующего пользователя при необходимости.
7. Выпустить собственные JWT и вернуть их клиенту в JSON; токен Яндекса не использовать как токен приложения и не хранить.

Login endpoint должен либо выполнить redirect на сформированный URL Яндекса, либо вернуть этот URL в JSON согласно принятому API-контракту. Не реализовывать оба варианта без необходимости. Callback возвращает JWT в JSON и не управляет frontend-навигацией.

Собственная аутентификация stateless:

- короткоживущий access JWT;
- долгоживущий refresh JWT;
- access и refresh token возвращаются клиенту в JSON и не помещаются в cookie;
- access token передаётся защищённым endpoint как Bearer token;
- refresh token передаётся refresh endpoint в JSON-теле запроса;
- серверные сессии и JWT в БД не хранятся;
- backend logout не реализуется: удаление клиентских токенов находится в ответственности frontend;
- не создавать denylist или хранилище сессий без отдельного требования.

Backend отвечает за выпуск и проверку JWT, но не за их хранение, автоматическое обновление или удаление на frontend. Не скрывать ограничения stateless-подхода в документации и тестах. Не логировать authorization code, OAuth-токены, JWT и секреты.

## Правила кода

- Использовать современный синтаксис Python и полную типизацию публичных функций, методов и значимых локальных структур.
- Не использовать `Any`, `cast`, `# type: ignore` и подавление линтеров без локального объяснения причины.
- Предпочитать небольшие функции и явные зависимости скрытому глобальному состоянию.
- Использовать `async` только для реального асинхронного I/O. Не объявлять функции асинхронными формально.
- Не выполнять блокирующий I/O внутри event loop.
- Не ловить `Exception`, если можно обработать конкретную ошибку. Не проглатывать исключения.
- Доменные и прикладные ошибки преобразовывать в HTTP-ответы на границе API, а не внутри бизнес-сервисов.
- Использовать timezone-aware UTC `datetime`.
- UUID генерировать на стороне приложения, если конкретная задача не требует иного.
- Конфигурацию читать через единый типизированный объект settings. Секреты получать из окружения и не коммитить.
- Не вводить булевы параметры, резко меняющие поведение функции; предпочитать отдельные явно названные операции.
- Комментарии должны объяснять причины и ограничения, а не пересказывать код.
- Публичные имена, код и техническая документация — на английском. Пользовательский текст может быть на русском.

## API и ошибки

- Маршруты должны быть тонкими и не содержать SQLAlchemy-запросов или правил аутентификации.
- Явно описывать response model, успешные статусы и ожидаемые ошибки в OpenAPI.
- Использовать единообразный формат ошибок во всём API.
- Не возвращать внутренние исключения, SQL, секреты или ответы OAuth-провайдера клиенту.
- Различать ошибки клиента, отказ провайдера и временную инфраструктурную ошибку.
- Не добавлять version prefix и иные соглашения API без принятого проектного решения.

## База данных и миграции

- Использовать декларативное отображение SQLAlchemy 2.x с `Mapped[...]` и `mapped_column()`.
- Все обращения к PostgreSQL должны быть асинхронными.
- Изменение схемы БД обязательно сопровождается миграцией Alembic.
- Проверять autogenerated migration вручную: типы, ограничения, индексы, downgrade.
- Не редактировать уже применённую миграцию для изменения схемы; создавать следующую.
- Не использовать cascade delete неявно. Поведение удаления задавать осознанно на уровне БД и ORM.
- Не добавлять индексы без связи с конкретным запросом или ограничением целостности.

## Тестирование

По умолчанию каждое изменение поведения должно сопровождаться тестом на правильном уровне. Если конкретная задача явно исключает создание тестов или изменение тестовой инфраструктуры, это ограничение имеет приоритет: новые тесты не добавлять, существующую тестовую инфраструктуру не менять и отдельно подтвердить это в отчёте.

- Unit-тесты: бизнес-сервисы, JWT и изолированная логика без реальной БД и сети.
- Integration-тесты: репозитории, ограничения PostgreSQL, транзакции и миграции.
- API-тесты: маршруты, JSON-контракты токенов, Bearer-аутентификация, статусы, схемы и преобразование ошибок.
- Внешний OAuth API в автоматических тестах подменять контролируемой реализацией провайдера; тесты не должны зависеть от Яндекса или интернета.
- Проверять не только happy path, но и неверный/просроченный `state`, отказ обмена code, некорректный профиль, повторный вход, конкурентное создание аккаунта, просроченные и неверно подписанные JWT.
- Не ослаблять production-код исключительно ради тестов; использовать внедрение зависимостей на естественных границах.

Исправление бага должно включать регрессионный тест, который падал до исправления, кроме задач, явно исключающих создание тестов.

## Безопасность

- Следовать OAuth 2.0 Authorization Code flow и актуальной документации провайдера.
- Передавать подписанный короткоживущий `state` через URL авторизации и полностью проверять его до обмена code; не хранить `state` в cookie или серверной сессии.
- PKCE использовать, если он поддерживается выбранным потоком и клиентом.
- Валидировать JWT полностью: подпись, разрешённый алгоритм, срок действия, тип токена и обязательные claims.
- Access и refresh token должны различаться явным claim; refresh нельзя принимать вместо access.
- Не задавать алгоритм проверки JWT из заголовка токена без allowlist.
- Не использовать cookie для OAuth `state`, access JWT или refresh JWT и не добавлять cookie-настройки в конфигурацию.
- Не принимать произвольный frontend redirect URL из запроса; при необходимости использовать значение из конфигурации или строгий allowlist.
- Не помещать секреты и персональные данные в URL, логи и сообщения ошибок.
- Не принимать решения о криптографии самостоятельно: использовать поддерживаемые библиотеки и стандартные примитивы.

## Документация и решения

`README.md` должен позволять новому разработчику:

- понять назначение и текущие возможности проекта;
- запустить приложение и PostgreSQL локально;
- применить миграции;
- запустить все проверки;
- настроить OAuth без раскрытия секретов;
- понять поток аутентификации и его ограничения.

Существенные компромиссы документировать кратко. ADR добавлять только для решений, которые действительно сложно восстановить из кода и README; не создавать ADR для каждого изменения.

## Порядок работы агента

Перед изменениями:

1. Прочитать связанные файлы, тесты, конфигурацию и миграции.
2. Проверить локальные инструкции в более глубоких `AGENTS.md`; они имеют приоритет для своего каталога.
3. Сформулировать минимальный объём изменений и не расширять задачу без необходимости.
4. Если требование допускает существенно разные варианты с разными последствиями, задать вопрос. Мелкие детали решать самостоятельно в рамках этого файла.

Во время реализации:

- сначала сохранять корректность и простоту, затем устранять очевидное дублирование;
- использовать существующие проектные соглашения;
- не реализовывать персонажей, навыки, дополнительные OAuth-провайдеры и инфраструктуру «заодно»;
- не добавлять заглушки, `TODO` и мёртвые расширения, если задача их не требует;
- для внешних API сверяться с актуальной официальной документацией.

Перед завершением:

1. Запустить релевантные проверки и сообщить точные результаты.
2. Просмотреть diff на предмет секретов, случайных файлов и лишних изменений.
3. Проверить, что миграции и документация соответствуют коду.
4. Кратко перечислить сделанное, принятые компромиссы и то, что проверить не удалось.

## Definition of Done

Задача завершена, когда:

- реализовано только согласованное поведение;
- архитектурные границы не нарушены без объяснимой причины;
- код типизирован и читаем;
- добавлены или обновлены релевантные тесты, если они не исключены условиями конкретной задачи;
- все доступные проверки проходят;
- схема БД сопровождается корректной миграцией;
- OpenAPI и README обновлены, если изменился внешний контракт или запуск;
- в коде, логах, fixtures и истории изменений нет секретов;
- существенные решения и компромиссы кратко отражены в коде или документации.
