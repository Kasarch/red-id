# AGENTS.md

## Область действия

Этот файл содержит обязательные правила работы с репозиторием RedID. Правила действуют для всего репозитория, если вложенный `AGENTS.md` не устанавливает более конкретные требования для своей директории.

Перед изменениями:

1. Прочитай этот файл и все вложенные `AGENTS.md`, применимые к изменяемым файлам.
2. Изучи структуру проекта, конфигурацию, существующую реализацию и тесты.
3. Проверь состояние Git и сохрани незакоммиченные изменения пользователя.
4. Не предполагай то, что можно проверить непосредственно в коде.

Не создавай коммиты, ветки, pull request и не выполняй deployment без прямого запроса пользователя.

## Общие принципы

- Исправляй первопричину проблемы, а не только её проявление.
- Не изменяй посторонние части проекта.
- Сохраняй существующую архитектуру и принятые соглашения, если задача явно не требует обратного.
- Не усложняй решение без практической необходимости.
- Не добавляй неиспользуемые абстракции, зависимости и инфраструктурные компоненты.
- Не скрывай ошибки отключением проверок, ослаблением типов или изменением тестов под неверное поведение.
- Не добавляй глобальные `# noqa`, `# type: ignore` и исключения coverage ради прохождения CI.
- Не раскрывай секреты, SQL, traceback, сообщения драйвера или внутреннее устройство приложения в публичных ошибках.
- Используй английский язык для идентификаторов и сообщений кода. Соблюдай язык и стиль существующей документации.

## Архитектура backend

Сохраняй направление зависимостей:

```text
HTTP route → service → repository → PostgreSQL
                    ↓
               domain model
```

Правила:

- route отвечает за HTTP, авторизацию, разбор входных данных и преобразование результата в ответ;
- бизнес-логика находится в domain/service, а не в route;
- service координирует прикладной сценарий и границы транзакции;
- repository инкапсулирует доступ к данным;
- route не выполняет SQL напрямую;
- repository не формирует HTTP-ответы;
- domain не зависит от FastAPI, SQLAlchemy и деталей транспорта;
- ожидаемые доменные и инфраструктурные ошибки преобразуются в публичные ошибки на установленной проектом границе;
- не перемещай исходный код и не перестраивай проект на другую архитектуру без необходимости.

## API

Все прикладные API endpoints должны оканчиваться символом `/`.

Примеры:

```http
GET /characters/
GET /characters/{character_id}/
POST /characters/
PUT /characters/{character_id}/
PATCH /characters/{character_id}/
DELETE /characters/{character_id}/
```

Правила:

- используй фактический API prefix проекта;
- не полагайся на автоматический redirect как на замену правильно объявленному маршруту;
- не добавляй одновременно варианты маршрута с `/` и без `/`;
- соблюдай заявленные HTTP status codes;
- ответ `204 No Content` не должен содержать тело;
- используй единый публичный формат ошибок;
- не раскрывай существование чужого ресурса, если проект использует политику сокрытия ресурсов;
- операции над ресурсом выполняются только для авторизованного владельца, если иное явно не предусмотрено требованиями;
- изменение названия персонажа выполняется только через общие `PUT` и `PATCH` ресурса;
- не создавай отдельный endpoint `rename` и не сохраняй несколько публичных способов изменения `title`;
- `PUT` сохраняет семантику полной замены ресурса;
- `PATCH` изменяет только явно переданные поля и различает отсутствующее поле и явно переданный `null`.

## Доменная модель

- Доменные инварианты должны быть сформулированы явно и проверяться в подходящем слое.
- Не допускай расхождения между domain, Pydantic-схемами, SQLAlchemy metadata и PostgreSQL constraints.
- Не добавляй произвольные игровые ограничения, которых нет в требованиях или доменной модели.
- Нормализация данных не должна незаметно менять их смысл.
- Для названия персонажа удаляй только пробелы по краям, если иное не установлено доменной моделью.
- Сохраняй отображаемый регистр названия.
- Уникальность названия персонажа для владельца должна обеспечиваться PostgreSQL без учёта регистра.
- Предварительная проверка конфликта допустима для понятной ошибки, но не заменяет constraint или unique index в базе данных.
- Конкурентный конфликт базы данных должен преобразовываться в тот же бизнес-конфликт, что и конфликт предварительной проверки.
- Не преобразовывай произвольный `IntegrityError` в конкретную доменную ошибку: определяй нарушенное ограничение устойчивым способом.

## Pydantic

Используй Pydantic v2 и актуальный стиль конфигурации моделей.

Правила:

- разделяй входные и выходные схемы, если их семантика различается;
- не принимай от клиента поля, которыми должен управлять сервер;
- PATCH-схемы должны отличать отсутствующее поле от явно переданного `null`;
- PUT должен сохранять семантику полной замены ресурса;
- ограничения схем не должны противоречить доменной модели и базе данных;
- сериализация должна быть явной и предсказуемой;
- не используй устаревшие API Pydantic v1.

## SQLAlchemy и транзакции

- Соблюдай принятый проектом async/sync-подход.
- Границы транзакции должны быть явными и согласованными.
- После ошибки записи выполняй rollback до дальнейшего использования сессии.
- Не оставляй сессию в сломанном транзакционном состоянии.
- Не выполняй commit внутри вспомогательных методов repository, если транзакцией управляет service или unit of work.
- Обрабатывай только ожидаемые ошибки; непредвиденные ошибки не маскируй под бизнес-конфликты.
- Ошибка repository или базы данных должна приводить к корректному rollback.

## Alembic и схема базы данных

- Любое изменение схемы оформляй новой Alembic-миграцией.
- Не редактируй уже применённые миграции задним числом.
- SQLAlchemy metadata и миграции должны совпадать.
- У constraints и indexes должны быть явные, стабильные и понятные имена.
- Реализуй корректные `upgrade()` и `downgrade()`.
- `downgrade()` должен отменять именно изменения соответствующей миграции.
- Перед добавлением constraint оцени существующие данные. Не удаляй и не исправляй их молча.
- Если данные могут нарушать новый constraint, выбери безопасную стратегию миграции и опиши риск.
- PostgreSQL-specific поведение проверяй на PostgreSQL, а не на SQLite.

### Автоматическое применение миграций в Docker

При каждом запуске backend-контейнера Alembic-миграции должны автоматически применяться до запуска приложения.

Обязательная последовательность:

```text
запуск контейнера → alembic upgrade head → запуск backend
```

Требования:

- автоматический запуск реализуется в Docker entrypoint или стартовой команде backend-контейнера;
- используй exec-форму или корректную передачу сигналов основному процессу;
- backend запускается только после успешного `alembic upgrade head`;
- при ошибке миграции контейнер завершается с ненулевым кодом;
- не подавляй ошибку Alembic с помощью `|| true` или аналогичных конструкций;
- не запускай приложение с неактуальной схемой;
- перед миграцией база данных должна быть доступна; используй существующий healthcheck/механизм ожидания готовности, если он предусмотрен проектом;
- повторный запуск контейнера должен быть безопасен: Alembic применяет только отсутствующие миграции;
- ручная команда Alembic сохраняется для локальной разработки, диагностики, проверки upgrade/downgrade и аварийных операций, но не заменяет автоматический запуск в контейнере;
- не создавай отдельный постоянно работающий сервис миграций, если это не требуется существующей архитектурой;
- если запускается несколько реплик backend, учитывай риск одновременного применения миграций и не добавляй неподтверждённых заявлений о полной безопасности такого запуска;
- README на русском и английском должен прямо описывать автоматическое применение миграций при старте backend-контейнера.

## Docker и Docker Compose

- Backend-контейнер автоматически применяет `alembic upgrade head`, а затем запускает приложение.
- Ни один сервис не должен иметь `restart: always` или `restart: unless-stopped`.
- Предпочтительно не указывать `restart`, чтобы запуск Docker daemon не запускал сервисы проекта автоматически.
- Не добавляй секреты в Dockerfile, Compose, image layers или логи.
- PostgreSQL внутри Compose должен быть доступен по имени сервиса, а не через `localhost`.
- `.env.example` содержит только безопасные фиктивные значения.
- Не коммить локальный `.env`.
- Не удаляй volumes во время проверок.
- Не используй `docker compose down --volumes`.
- При изменении entrypoint сохрани корректную передачу сигналов и exit code приложения.
- Healthcheck должен проверять реальную готовность сервиса, если он присутствует.

## JWT и OAuth

Сохраняй установленную архитектуру stateless JWT, если отдельная задача явно не меняет её.

- Не добавляй Redis, таблицу сессий, blacklist или хранение refresh-токенов без архитектурного решения.
- Обязательно различай access token, refresh token и OAuth state.
- Проверяй `exp`, `iat`, `sub` и назначение токена.
- Проверяй issuer и audience, если они предусмотрены конфигурацией.
- Access token нельзя использовать как refresh token и наоборот.
- OAuth state нельзя использовать как access или refresh token; access/refresh token нельзя использовать как OAuth state.
- Не называй повторную выдачу пары токенов безопасной rotation, если сервер не способен обнаружить повторное использование старого refresh-токена.
- Не выводи JWT, OAuth code, OAuth state, client secret и другие чувствительные данные в логи.
- Документация должна честно описывать ограничения stateless refresh-токенов и отсутствие мгновенного серверного отзыва, если это соответствует реализации.

## Тестирование

Любое изменение поведения должно сопровождаться тестами.

Для исправления ошибки сначала добавь тест, воспроизводящий проблему, если это практически возможно.

Проверяй:

- успешный сценарий;
- граничные значения;
- некорректные входные данные;
- бизнес-конфликты;
- отсутствие ресурса;
- доступ к чужому ресурсу;
- ошибки repository или базы данных;
- rollback транзакции;
- регистронезависимые ограничения;
- заявленные HTTP status codes;
- отсутствие тела у ответа `204`;
- наличие завершающего `/` у API endpoint;
- недопустимость случайного использования варианта маршрута без `/`, если приложение настроено без автоматических redirects;
- автоматический запуск миграций до backend-процесса в контейнере при изменении Docker entrypoint или команды запуска;
- завершение контейнера/entrypoint с ненулевым кодом при ошибке миграции, если это практически возможно проверить автоматически.

Тесты должны быть:

- независимыми от порядка выполнения;
- детерминированными;
- изолированными;
- понятными по названию;
- сосредоточенными на наблюдаемом поведении;
- без реальных сетевых запросов к OAuth-провайдерам;
- без реальных секретов.

Не изменяй тест так, чтобы скрыть реальную регрессию. Исправляй причину ошибки в коде.

Моки используй на границах системы. Не подменяй моками проверяемую бизнес-логику.

Для database-specific поведения, включая PostgreSQL constraints и конкурентные конфликты, используй интеграционные тесты с PostgreSQL, а не SQLite.

Не снижай порог coverage ради зелёного CI. Не добавляй фиктивные coverage badges.

## Обязательные проверки

После изменений выполни доступные проверки из каталога backend:

```bash
poetry check
poetry run ruff format --check .
poetry run ruff check .
poetry run mypy src
poetry run pytest
```

Если изменены зависимости:

```bash
poetry lock
poetry install
```

Если изменены Dockerfile, Compose, entrypoint или команда запуска:

```bash
docker compose config
docker compose build backend
```

Дополнительно проверь фактический запуск контейнера:

1. Запусти необходимые сервисы без удаления существующих volumes.
2. Убедись по exit code и логам, что `alembic upgrade head` выполнился до запуска backend.
3. Убедись, что backend не стартует при ошибке миграции, если такую проверку можно безопасно выполнить.
4. Проверь health/status контейнеров и базовый API smoke test.
5. Останови сервисы без удаления volumes.

Не применяй миграции вручную перед smoke test контейнера: иначе проверка не подтвердит автоматический запуск на старте. Ручной запуск допустим отдельно для проверки обратимости миграции.

Если изменена схема базы данных, выполни отдельную проверку миграции:

```bash
poetry run alembic upgrade head
poetry run alembic downgrade -1
poetry run alembic upgrade head
```

Команды необходимо адаптировать к фактическим путям, именам сервисов и конфигурации проекта.

Не объявляй проверку успешной, если она:

- не запускалась;
- была пропущена;
- завершилась ошибкой;
- недоступна в текущем окружении.

В итоговом отчёте укажи точный результат каждой выполненной проверки и причину для каждой невыполненной.

## Формат итогового отчёта

После выполнения задачи сообщи:

1. Что было изменено.
2. Какие файлы созданы или изменены.
3. Какие тесты добавлены или обновлены.
4. Результаты Ruff, mypy и pytest.
5. Результаты Alembic, Poetry и Docker-проверок, если они относятся к задаче.
6. Подтверждение, что автоматическая миграция выполняется до запуска backend-контейнера.
7. Результат проверки поведения при ошибке миграции либо причину, по которой она не выполнялась.
8. Какие проверки не удалось выполнить и почему.
9. Какие решения или компромиссы требуют внимания пользователя.

Перед завершением просмотри итоговый diff и удали случайные, временные и не относящиеся к задаче изменения.
